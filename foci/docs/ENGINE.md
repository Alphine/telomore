# Foci Lab analysis engine (`foci/web/engine/`)

The 53BP1 focus counter of `src/telomere_lab/foci/segment.py`, re-implemented in plain JavaScript so the analysis
runs **in the user's own browser** (CPU reference path, optional WebGPU path). The server never sees or computes
on user images. No framework, no build step, no dependencies, no network access.

| File | What |
|---|---|
| `engine.js` | the engine; classic script, defines `window.FociEngine` (and `module.exports` under Node) |
| `worker.js` | Web Worker shim used by `createPool()` (`importScripts('engine.js')`, same directory) |
| `parity.html` | browser page: golden fixtures in reference mode vs Python, and GPU vs reference (see "GPU status") |
| `dev/pngdecode.js` | tiny greyscale PNG decoder (8/16-bit) used by tests and `parity.html`; not loaded by the engine |
| `dev/bench.mjs` | CPU benchmark (`node foci/web/engine/dev/bench.mjs`) |

Tests: `foci/tests/engine-*.test.mjs` (Node built-in runner). Fixtures: `foci/tests/fixtures/engine_golden/`,
generated by `scripts/make_engine_fixtures.py`, drift-checked by `tests/test_foci_engine_fixtures.py`.

## API

```js
FociEngine.version                       // '1.0.0' (also in every result)
await FociEngine.capabilities()          // {webgpu, adapter:{vendor,architecture,description,limits}|null,
                                         //  selfTest:'passed'|'failed'|'skipped', maxImagePixels, hardwareConcurrency}
FociEngine.defaultParams()               // fresh object == FociParams() in segment.py
await FociEngine.analyze(input, opts?)
FociEngine.createPool(n?, popts?)        // -> {analyze(input, opts), terminate(), size, inline}
await FociEngine.parity(cases)           // GPU-vs-reference report (see below)
```

`input = {dna, foci, params?}`; `Channel = {data, width, height, bitDepth}` with `data` a `Uint8Array` (bitDepth 8),
`Uint16Array` (12 or 16) or `Float32Array` (32). Both channels must have the same size. `params` is a partial
`{nucleus_sigma, background_size, min_nucleus_px, foci_sigma, tophat_size, min_height, peak_window}`.

`opts = {mode:'auto'|'reference'|'gpu' (default 'auto'), overlay:boolean, signal:AbortSignal,
maxImagePixels (default 16e6, per channel), maxMemoryBytes (default 1.6e9, estimated working memory), batchSize}`.
`opts.debug:true` adds `result._debug` (intermediate arrays; used by the tests and the parity report; do not use in production).

Result:

```js
{ version, backend:'cpu-f64'|'webgpu-f32', timing_ms:{total, <stage>...}, image:{width,height},
  normalisation:{dna:{bit_depth,method,lo,hi,clipped_fraction,clipped_high_fraction,clipped_low_fraction,saturated_fraction}, foci:{...}},
  nuclei:{count, object_count, objects:[{id, area_px, cx, cy, nuclei_in_object, foci}]},
  foci:{count, per_cell:number|null, points:[{x, y, height, object}]},
  thresholds:{nucleus, nucleus_float32, nucleus_log, min_height_float32},
  params, warnings:[...], overlay?:{width, height, data:Uint8ClampedArray /* RGBA, alpha 255 */} }
```

* `nuclei.count` is the area-based estimate exactly as `count_foci` computes it (`n_nuclei`); `nuclei.object_count`
  (= `objects.length`) is the number of connected objects. `nuclei_in_object` is the per-object estimate (>= 1).
* `objects[i].id` is the 1-based label; `cx, cy` are the centroid in pixels, **unrounded** (Python's `nucleus_table` rounds to 0.1).
* `points` are the counted foci in raster order (same order as `np.nonzero`); `height` is the float32 top-hat value,
  `object` the owning nucleus object id. `foci.per_cell = foci.count / nuclei.count`, `null` when there are no nuclei.
* `overlay` replicates `overlay_rgb` byte for byte at full size. (The server block-reduces images above 2048 px before drawing;
  the engine does not: downscale in the page if needed.)
* `normalisation.*.method`: `'none'` (8-bit as is), `'percentile-0.1-99.99'`, or `'flat'` (no intensity range: the channel becomes all zero, as in Python).
  `clipped_fraction` = pixels clipped at either end; `clipped_high_fraction` is Python's number.

### Errors

Every rejection is an `Error` with `.code`:

| code | when |
|---|---|
| `bad_input` | wrong shape/type/bit depth, size mismatch, non-finite float pixels, 12-bit values > 4095, parameter out of range / not odd / unknown, float32 range that overflows the stretch |
| `too_large` | more than `maxImagePixels` per channel (default 16 Mpx), an edge > 65535, estimated memory above `maxMemoryBytes`, or (explicit `gpu` mode only) a plane larger than the GPU's storage-buffer limit; decided **before** anything is allocated |
| `aborted` | `AbortSignal` fired (also: pool terminated, pool timeout) |
| `gpu_lost` | `mode:'gpu'` but WebGPU is missing / self-test failed / device lost / a GPU error occurred |
| `internal` | (pool only) a worker crashed; extra code, not part of the four above |

`mode:'auto'` never throws `gpu_lost`: it falls back to the CPU and says so in `warnings`. After a device loss or a GPU error the
engine stays on the CPU for the rest of the session (`warnings` mention it). `analyze()` yields to the event loop between stages
**only when a `signal` is given**, so an abort takes effect at the next stage boundary (a few tens of ms); a stage itself is not interruptible
on the calling thread (use the pool: it terminates the worker).

### Parameter ranges (same as `backend/foci_upload.py` `PARAM_SPECS`)

`min_nucleus_px` int 20..100000; `background_size` odd int 11..301; `min_height` 0.5..255; `tophat_size` odd int 3..51;
`peak_window` odd int 3..31. `nucleus_sigma`, `foci_sigma` (not tunable on the server): 0.1..10. Even window sizes are rejected
(scipy's even-size origin rules are not implemented and the server rejects them too).

### Worker pool

`createPool(n?)` with `n` defaulting to `min(hardwareConcurrency - 1, 4)` (at least 1). Tasks queue FIFO; each worker runs one analysis at a time.

* **Buffers are transferred** (`postMessage` transfer list): after `pool.analyze(input)` the caller's `dna.data` / `foci.data` are **detached (length 0)**.
  Pass `{transfer:false}` in the analyze options to send copies instead. Views that do not cover their whole `ArrayBuffer` are always copied.
* The overlay buffer is transferred back.
* `signal` abort on a *queued* task removes it; on a *running* task the worker is terminated (a synchronous analysis cannot be interrupted) and replaced lazily.
  Per-task timeout `timeoutMs` (pool option, default 300000) does the same with code `aborted`. `terminate()` rejects everything outstanding and all later calls.
* Images are posted only after the worker said it is ready; if a worker cannot start (for example CSP `worker-src`), the task runs on the calling thread instead
  of failing, and the images are still intact.
* Under Node (and when `Worker` is missing) the pool runs inline, sequentially (`pool.inline === true`). `createPool(n, {inline:false})` forces worker mode.
* Cache busting: the pool starts `worker.js?v=TOKEN`, where TOKEN is the `v=` value of the `<script src="engine.js?v=HASH">` tag (the deploy step
  `scripts/stamp_foci_assets.py` adds it) or `FociEngine.version`; `worker.js` passes the same token to `importScripts('engine.js?v=TOKEN')`.
  A change to `worker.js` alone does not change that token: bump `VERSION` in `engine.js` when `worker.js` changes.
* CSP: needs `script-src 'self'` and `worker-src 'self'`; nothing else (no `unsafe-eval`, no `blob:`, no WebAssembly, no `connect-src`).

## What is computed (segment.py, step by step)

1. **Normalisation** (`to_signal`): 8-bit as is. 12/16/32-bit: 0.1 and 99.99 percentile (numpy `linear` interpolation, float32
   difference semantics) mapped to 0..255 with the same float32 operations (`a -= lo` in float64 stored float32; `a *= float32(255/(hi-lo))`), then clipped.
   Equal percentiles: all zeros, `method:'flat'`. Reported, never silent.
2. **Nuclei**: `gaussian_filter(float32, nucleus_sigma)` (scipy kernel, `truncate=4`, reflect, axis 0 then 1, float32 stored after each pass,
   numpy's pairwise-summed normalisation, scipy's symmetric-kernel summation order) -> minus `grey_opening(size=background_size)` (separable
   van Herk min/max, exact, reflect at any distance) -> `_log_otsu` (float32 `log1p`, `np.histogram` with its float32 `linspace` edges and index
   arithmetic, float64 `otsu_threshold`, `expm1`, compared as float32) -> `binary_opening(iterations=2)` (4-connected) -> `binary_fill_holes`
   -> 4-connected labelling in raster order, objects below `min_nucleus_px` dropped, consecutive relabel.
3. **Nucleus count**: `max(1, rint(area / median(area)))` per object (half-to-even), summed.
4. **Foci**: only if at least one object exists (as in Python). `gaussian_filter(foci, foci_sigma)` -> `white_tophat(size=tophat_size)`
   -> peak = `th == maximum_filter(th, peak_window)` and `th >= float32(min_height)` and inside an object. Equal maxima on a plateau are all
   counted (no tie-breaking), exactly as in Python.
5. **Overlay**: `overlay_rgb` (1 / 99.7 percentile stretch, blue = DNA x 0.85, green = 53BP1, red = 0.25 x 53BP1, outline = inside & not eroded,
   amber rings = dilation(3) minus dilation(1) of the focus pixels; float32 x 255 truncated to uint8).

## Modes, determinism and precision statement

### `mode: 'reference'` (CPU, backend `cpu-f64`)

Float64 arithmetic with float32 *storage* at exactly the points where numpy/scipy store float32 (see above). **Results equal the Python
ones bit for bit** on all 36 golden fixtures (24 synthetic including 8/12/16-bit, saturated, constant, empty, tiny, 1xN, Nx1, non-square; 12 real
IDR idr0010 pairs) and all 48 parameter-sweep runs (3 fixtures x 16 variations of `min_height`, `tophat_size`, `peak_window`,
`background_size`, `min_nucleus_px`):

| quantity | parity |
|---|---|
| normalised channels, smoothed DNA, `flat`, smoothed foci, top-hat (sha256 of the float32 bytes) | identical |
| nucleus label image (sha256 of int32) | identical |
| object count, estimated nuclei, per-object foci, object areas, every peak (x, y, height, object) | identical |
| overlay RGB (sha256) | identical |
| nucleus threshold as **float32** (the only form in which it is used) | identical |
| nucleus threshold as **double** | differs by <= 1 ulp in some cases (`Math.expm1` vs numpy's libm `expm1`); tests allow 4 ulp |

Residual risk, stated plainly: the JS engine's `Math.exp`, `Math.log1p` and `Math.expm1` are not bit-identical to numpy's libm
(measured against this machine's numpy 2.3.4: float32 `log1p` differs from `fround(Math.log1p(x))` for 8% of random inputs, `exp` and `expm1`
for ~10-19% at the last double bit). `exp` only feeds the Gaussian kernel (kernels for sigma 1, 2, 3 are bit-identical to scipy's; a last-bit
difference would flip a float32 rounding with probability ~1e-9 per pixel), `log1p` only feeds histogram binning. Measured effect of the `log1p`
difference on the 106 cached real IDR images (34.5 Mpx): **2 pixels** fell into a different histogram bin, in 2 images, and **0 of 106**
Otsu thresholds changed. Python itself is platform dependent in the same way (numpy on Linux/SVML vs Windows use different `log1p`
implementations), so "identical to Python" can only mean "identical to the numpy build that made the fixtures" (numpy 2.3.4, scipy 1.18.0,
Windows x64). Other JS engines may have a different `Math.exp`/`log1p` from V8; the fixtures are what to run there.
Everything else is IEEE-754 double/float32 arithmetic and is deterministic across engines and machines.

Identical input gives identical output (tested, including overlay). The engine never mutates its inputs.

### `mode: 'gpu'` (WebGPU f32, backend `webgpu-f32`)

GPU: separable Gaussian, separable min/max for opening / top-hat / maximum filter, `A - B` subtraction, peak flags (`th == max && th >= minh`),
all in float32 storage buffers (one thread per pixel, loops over the window, reflect index in the shader).
CPU (same code as reference): normalisation, **log/Otsu (histogram and threshold)**, thresholding, morphology, hole filling, labelling,
object statistics, nucleus estimate, peak collection, overlay. Reasons: anything that feeds a threshold or a count is computed by one
deterministic implementation that cannot differ between GPUs (no GPU `log`, no GPU float histograms, no atomics), and the integer/graph algorithms
have no speed to gain at these sizes.

What differs from the reference: only the float32 values of the filters. Shaders cannot guarantee operation order or FMA contraction, so each GPU
may round differently in the last float32 bits. Measured (AMD gcn-5, Chromium 152): **max |difference| 3.1e-5 (smoothed DNA), 4.6e-5 (flat),
3.1e-5 (top-hat)** on 0..255 data, i.e. float32 accumulation noise. A count or a peak can differ only if a pixel lies within that distance of a
threshold or ties with a neighbour within that distance; on the 3 measured images (see below) counts, labels, per-object foci and all peak
coordinates were **identical** to the reference. There is no guarantee of identity across GPUs: the GPU result is "reference within float32 noise",
and `parity()` / `parity.html` exist to measure exactly that on the user's hardware. For science that must equal Python, use `mode:'reference'`.

Every GPU pass uses distinct source/destination buffers, placeholder buffers per binding role (WebGPU forbids binding one buffer both read-only and
writable in a dispatch), and runs inside `pushErrorScope('validation'/'out-of-memory')`; any error becomes `gpu_lost` and, in `auto` mode, a CPU re-run.

**Boot self-test** (first use of the GPU, also triggered by `capabilities()`): a 64x48 synthetic pair with two planted foci goes through both
backends; requires max |difference| <= 0.05 for the DNA `flat` and top-hat arrays and *identical* peak flags, and at least two peaks. Failure sets
`selfTest:'failed'`, forces the CPU and is reported in `warnings` (auto) or as `gpu_lost` (explicit gpu). Measured on the test machine: flat 3.1e-5, top-hat 1.1e-5, 0 peak mismatches.

### `mode: 'auto'` (default) - the rule

GPU only when **all** hold: `navigator.gpu` exists, the self-test passed, no earlier device loss/error in this session, and
(`pixels >= 2,000,000` per channel, **or** `opts.batchSize >= 8` and `pixels >= 250,000`). Otherwise the CPU reference path. Rationale: the CPU reference is
exact, so it is preferred unless speed matters. The thresholds are a prior: on the one GPU measured (integrated Vega) the GPU was already ~2x faster at
0.36 Mpx, but GPUs differ wildly and results are only "within float32 noise", so the default favours exactness. Callers that want to decide differently pass
`mode` explicitly. Batch callers should pass `batchSize` (the number of images they are about to analyse).

### Memory

Estimated before allocating: about 30 bytes per pixel (38 with overlay) of engine working memory per analysis (two float32 work buffers, masks, int32 labels,
flood-fill stack, peak mask; plus the caller's own input). 16 Mpx therefore needs ~0.5 GB (0.6 GB with overlay); the default limit is 1.6 GB (`maxMemoryBytes`).
Each pool worker holds its own copy: 4 workers on 16 Mpx images can approach 2-3 GB, so lower `maxImagePixels` or the pool size on memory-poor devices.
GPU sessions add 4 buffers of 4 bytes/pixel on the device (the 16 Mpx maximum fits the default 128 MiB `maxStorageBufferBindingSize`).

## Benchmarks (CPU reference)

`node foci/web/engine/dev/bench.mjs` on the development laptop (AMD Ryzen 5 PRO 5650U, Node 22.23, Windows 11, median of 5 after warm-up):

| image | engine, Node 22 | Python `count_foci` (scipy 1.18, same machine) |
|---|---|---|
| 696 x 520 (0.36 Mpx, IDR field) | **97 ms** (min 88) ; with overlay 141 ms | 61 ms |
| 2784 x 1560 (4.34 Mpx, tiled) | **1067 ms** ; with overlay 1640 ms | 661 ms |

Stage breakdown, 4.3 Mpx: Gaussians 0.2 + 0.12 s, erode/dilate (van Herk) 0.3 + 0.37 s, log-Otsu 0.18 s, morphology + fill + label 0.29 s,
overlay 0.43 s. So the JS reference is ~1.6x slower than scipy's C on one core; in Chromium (inside the Claude desktop app) the same code measured
~0.21-0.25 s for the 0.36 Mpx field and 1.4-1.9 s for 4.3 Mpx (including the first-call JIT and a busy machine).

GPU (same machine, Chromium 152 in the Claude desktop app, AMD gcn-5 integrated; `mode:'gpu'` whole `analyze()`, 3 runs after warm-up; the CPU rows are the reference in the same page):

| image | reference | gpu (whole analyze) | GPU filters alone (DNA + foci incl. upload/readback) |
|---|---|---|---|
| synthetic 696x520 | 207-252 ms | 112-120 ms | 40 + 26 ms |
| synthetic 696x520 (seed 2) | 137-176 ms | 96-107 ms | 41 + 23 ms |
| synthetic tiled 2784x1560 | 1.41-1.88 s | 0.91-1.15 s | 256 + 218 ms |

Only ~half of the GPU path is GPU time: Otsu, morphology, labelling, peak collection stay on the CPU.

## GPU status: what was and was not tested

* **Tested (once, by hand, this machine only):** WebGPU exists in the Claude desktop app's Chromium (152.0.7977.130) on an AMD Radeon (gcn-5, integrated).
  The self-test passed and a CPU-vs-GPU comparison on 3 synthetic IDR-like images (2 x 696x520, 1 x 2784x1560) gave identical counts, per-object foci,
  labels and peaks with the float differences quoted above. This was run by pasting a **condensed copy** of `engine.js` into a page (the pipeline, WGSL,
  `GpuSession`, both GPU backends and the self-test are verbatim; input validation, the pool and overlay were left out), because the sandbox could not serve
  files over HTTP.
* **Not tested:** any other GPU/driver/browser (Intel, NVIDIA, Apple, Firefox, Safari, Android); the GPU path running *inside a Web Worker*; `device.lost`
  recovery on a real lost device (only the fallback logic is unit-tested with a faked state); out-of-memory behaviour near 16 Mpx; GPU results on the real golden
  fixtures (`parity.html` was written for this but has not been run in a browser - run it: serve the repo root and open `/foci/web/engine/parity.html`);
  GPU behaviour on tiny, 1xN, Nx1 and windows-larger-than-the-image inputs (the shader uses the same reflect formula as the CPU, and the CPU formula is tested
  against scipy, but the WGSL one is not).
  Shader source is not testable in Node; the Node suite covers the GPU *selection* logic (no WebGPU, failed self-test, lost device), not the shaders.
* The naive O(window) min/max shader does 41 reads per pixel per pass at the default size and up to 301 at the maximum `background_size`; van Herk on the GPU
  would be faster for big windows but was not implemented (not needed for correctness).

## Tests and fixtures

```bash
node --test "foci/tests/*.test.mjs"                       # all site tests incl. engine-*.test.mjs (about 12 s)
python -m pytest tests/test_foci_engine_fixtures.py -q -p no:warnings   # fixtures still match segment.py
PYTHONPATH=src python scripts/make_engine_fixtures.py     # regenerate PNGs + manifest (needs .cache/idr0010/img/*.npz)
PYTHONPATH=src python scripts/make_engine_fixtures.py --check           # verify, no writes
PYTHONPATH=src python scripts/make_engine_fixtures.py --dump DIR CASE   # raw float32 intermediates of one case, to diff by hand
```

| test file | what |
|---|---|
| `engine-golden` | exact parity on 36 fixtures incl. intermediate-array hashes |
| `engine-sweep` | exact parity on 48 parameter variations; `defaultParams` == `FociParams()` |
| `engine-normalise` | normalisation bit-exact vs `to_signal`; 8/12/16/32-bit; constant, saturated, hot pixel, no `Uint16` wrap-around, float overflow |
| `engine-kernels` | Gaussian weights == scipy's, reflect index, van Herk vs brute force (incl. windows larger than the image, 1xN), morphology, labelling order, `rint` |
| `engine-overlay` | overlay bytes == `overlay_rgb` for all fixtures; colours |
| `engine-guards` | too_large (pixels, edge, memory), bad_input (shape/type/NaN/Inf/params), abort (before and during), GPU selection/fallback logic, no input mutation, determinism, result shape, no-network/no-eval source scan |
| `engine-pool` | pool under Node (inline) |
| `engine-pool-workers` | the browser pool code path through real threads (a `Worker` shim on `worker_threads` running the real `worker.js`): transfer, abort kills the worker, timeout, crash, cannot-start fallback, leaks (`live == 0`) |

Fixtures are 2.7 MB. Synthetic PNGs are authoritative (numpy's generator stream may change; the PNGs do not). Real images: idr0010 (Doil et al., Cell 2009, CC BY 4.0).
`tests/test_foci_engine_fixtures.py` re-runs the Python reference on the stored PNGs: results (counts, per-object, peaks, areas) are compared strictly; the intermediate-array
hashes only on the same numpy/scipy/platform as the manifest (skipped, with the reason, elsewhere).

## Safety

* No `fetch`/XHR/WebSocket/`import()`/`eval`/`new Function`/remote `importScripts` anywhere in `engine.js` or `worker.js` (a test scans the source).
* Everything is validated before work starts (types, sizes, finiteness, parameter ranges, memory estimate), so malformed input cannot reach a worker or the GPU.
* Long work is abortable at stage boundaries (calling thread) or by terminating the worker; pools have a default 5-minute task timeout.
* Output is a plain value; the overlay is an RGBA `Uint8ClampedArray` the page can put on a canvas with `putImageData`. The engine writes nothing to the DOM.
